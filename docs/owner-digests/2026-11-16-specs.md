# Owner digest, 16 Nov 2026: specs waiting for your answers

Fourteen draft specs need your answers before anyone builds them. Each one below has a single line on what it
gives users, then its open questions. Every question puts the recommended answer first and then says what
changes if you answer no. Nothing here is built until you answer; "yes to all recommended" on a ticket is enough.

**Settle first.** The two conflicts that block other work are in the field-work digest
(`2026-11-16-field-work.md`): who owns a site's GPS boundary, and whether the daily site report can keep its pick
lists on the phone while offline. In this file, report templates waits on the daily site report, so it comes
after those two.

Count: 56 questions across 14 tickets.

---

## 1. Payables: what we owe suppliers (#1861)

Gives users one list of supplier invoices recorded in PMO and not yet paid, aged by invoice date, for the whole
company and per project, on the Growth plan and above.

1. Should the new "payables" plan setting alone switch the Payables page on, instead of today's procurement
   setting? **Recommend: yes.** Every plan that includes payables also includes procurement. If no: the page
   follows procurement as it does today, and a plan cannot sell payables on its own.
2. Should a project's payables figure show to everyone who can already see that project's money section,
   project managers included? **Recommend: yes.** If no: only finance roles see it, and project managers have to
   ask finance what their project owes.
3. Should the project filter on the company page include a "No project" entry for invoices with no project?
   **Recommend: yes, one entry.** If no: unassigned invoices show only in the unfiltered list and are easy to miss.

## 2. Profit and loss: gross margin first, on every plan (#1860)

Gives every plan a P&L that opens on gross margin (billed revenue less project costs, by month, with each
project's share), with overheads and net profit kept for Pro.

1. Should project cost mean money actually paid, with open commitments shown beside it but not subtracted?
   **Recommend: yes.** If no: margin includes orders not yet paid and looks worse than the cash reality, and it
   moves every time an order is placed.
2. Should revenue count by invoice date and cost by payment date, with ERP-connected companies getting monthly
   revenue but cost as a to-date total (the ERP figures carry no month)? **Recommend: yes.** If no: we have to
   build month-by-month cost from the ERP first, which is a larger job and delays the page.
3. Should there be one P&L page open to all plans, with the Pro-only blocks locked inside it? **Recommend: yes.**
   If no: we keep two pages, and users on lower plans can't see what Pro adds.

## 3. Google Calendar: milestones and deadlines (#1583)

Gives the team project phase dates and end dates in Google Calendar, kept up to date when dates move, plus
Google sign-in.

1. Should an Admin connect one shared company calendar, rather than each person connecting their own?
   **Recommend: one shared calendar now, personal calendars later.** If no: every user goes through Google
   consent, and the build grows to handle one connection per person.
2. Should only phase dates and project end dates go to the calendar? **Recommend: yes; add task and work-order
   dates when asked.** If no: calendars fill with many small items, and the first build is larger.
3. Can the first customer use an internal Google app that skips Google's public review? **Recommend: yes, and go
   through review only when a second company needs it.** If no: Google's review comes first and takes weeks
   before anyone can use it.

## 4. Report templates exported to PDF (#1582)

Gives an Admin named company templates that fill a daily site report or a progress report from PMO data and
download as a PDF with signature blocks. Waits on the daily site report.

1. Should only Admins design templates, with project managers picking from them? **Recommend: yes.** If no:
   more people can edit templates, and one could print data the client should not see.
2. Should the signature blocks be signed by hand on paper in the first release? **Recommend: yes.** If no: an
   in-app sign-off is a new approval step with its own separation-of-duties rules, and it ships as its own piece
   of work.
3. Should the PDF be produced on the server, rather than with the browser's print or the ERP's print formats?
   **Recommend: server.** It gives the same output every time, and daily site reports are not ERP records. A
   short trial picks the PDF tool and checks licence and Indonesian characters. If no: output varies by
   browser, or reports must exist in the ERP first.
4. Should a PDF only download unless the user chooses "Save to project documents"? **Recommend: yes.** If no:
   every export is stored automatically and the documents list fills with copies.
5. Should there be one company logo on all reports, rather than one per project or per client?
   **Recommend: one company logo.** If no: logo upload goes on every project or client, which adds work.
6. Should the progress report cover a calendar month, to match the monthly progress assessment?
   **Recommend: calendar month.** If no: users can pick any date range, and figures may not tie to the monthly
   claim.
7. Which plan includes report templates? **Recommend: Growth and above.** If no: Pro only, for example, and
   Growth customers keep retyping reports.
8. Should the daily site report take new database slots before this spec is planned (its planned slots are now
   used by other work)? **Recommend: yes.** If no: the two plans collide and planning stalls.

## 5. RFIs and submittals: who holds it and when it is due (#1581)

Gives a project a view of every open question to the client or engineer and every submittal waiting for
approval, showing who holds each one and when the answer is due.

1. Should outside parties only be recorded in the first version, with a staff member entering their reply?
   **Recommend: yes; a client portal is separate work.** If no: we build outside logins first, which is a much
   larger and riskier job.
2. May the person who raised an RFI record the outside party's answer to it? **Recommend: yes for outside
   answers only, stamped with the date received and the company. Inside answers still need someone other than the
   author.** If no: someone else must always type in a client's reply, which slows small teams.
3. Should Engineers raise RFIs and answer the ones assigned to them? **Recommend: yes, for these items only.**
   If no: engineers ask a project manager to do it for them, and the record shows the wrong author.
4. Should the first version notify people only when an item is handed over and when it is answered, with a
   manual "chase" button next? **Recommend: yes, and no automatic overdue reminder yet.** If no: we add a
   scheduled overdue reminder now, which is a larger build.
5. Should RFI numbers use the company's usual daily numbering, rather than numbering per project?
   **Recommend: company numbering; per-project only if a contract requires it.** If no: we build a second
   numbering scheme now.
6. Should issuing an RFI leave the due date blank and skip cost and schedule impact flags for now?
   **Recommend: yes.** If no: we add a default due period (7 or 14 days) and impact fields, which needs more
   design.
7. Is "Approved" plus a note enough for a submittal, without a separate "Approved as noted" result?
   **Recommend: yes.** If no: we add a new outcome, and every filter and report must learn it.

## 6. Company cost codes on budgets (#1580)

Gives a company its own list of cost codes below the standard categories, used on budget lines and orders,
with committed spend rolled up per code.

1. Should cost codes go up to three levels (division, section, item)? **Recommend: yes.** If no: either a flat
   list, which large contractors outgrow, or unlimited depth, which is harder to report on.
2. Should a cost code be optional on a line in the first version? **Recommend: yes; a company "required"
   switch comes later.** If no: every existing budget line needs a code before it can be saved.
3. Should cost codes stay in PMO only and not map to ERP accounts yet? **Recommend: yes.** If no: the budget
   push and the actuals pull both change, which touches the money path and is a larger job.
4. Should bulk import of a code list (pasting rows) come in a later slice? **Recommend: yes; the first version
   is manual entry.** If no: import is built now and delays the first release.
5. Should only Admins maintain the code list? **Recommend: yes.** If no: Finance and Executives also edit it,
   and codes can drift without one owner.
6. Should a code's default category only pre-fill the line, without forcing it? **Recommend: yes.** If no:
   lines whose category differs from the code's default are blocked.
7. Should every project see all of the company's active codes? **Recommend: yes, no per-project subsets yet.**
   If no: each project needs its own code setup.
8. Should only committed spend roll up to the code in the first version? **Recommend: yes; paid spend follows
   once the ERP question (3) is decided.** If no: we decide now how ERP-sourced costs get codes.

## 7. CRM: log an Outlook email or meeting to a contact (#1575)

Gives users a couple of clicks to file an Outlook email or meeting against a contact, so the account timeline
shows what was said.

1. Should an item be filed against a contact only, and not a company with no contact? **Recommend: contact only;
   the company page already shows its contacts' history.** If no: we add company-level logging, a second path to
   build and test.
2. Should we keep a short preview of the body (500 characters), not just the subject and a link?
   **Recommend: yes, and say so in the confirmation.** If no: the timeline shows only subjects, and you need
   Outlook open to know what was said.
3. Should email and calendar read access be asked for together in one reconnect? **Recommend: yes; the normal
   sign-in stays unchanged.** If no: users see two separate consent prompts.

## 8. Tasks: baseline vs actual dates and percent complete (#1574)

Gives the plan a frozen "what we promised" date for each task, drawn beside the live dates, and a percent
complete that rolls up the plan.

1. Should percent complete accept any whole number from 0 to 100? **Recommend: yes.** If no: steps of 10, which
   is quicker to enter but less precise.
2. May the person assigned a task set its percent complete, but not its baseline? **Recommend: yes.** If no:
   only project managers update progress, and it goes stale.
3. Should a baseline be settable for the whole project at once and also for a single task? **Recommend: both.**
   If no: whole project only, and adding one late task means re-baselining everything.

## 9. Budget: propose lines from an uploaded document (#1466)

Gives a budget editor proposed category, description and amount rows from a PDF, scan or spreadsheet, to check
in the usual preview and save to a draft.

1. Should PDFs and images go to our AI model provider only when the user opts in for that file, with a short
   notice, while spreadsheets are read inside PMO only? **Recommend: yes.** If no: either no PDF or image
   support, or files leave PMO without asking.
2. Should the uploaded file be thrown away after the proposal, with users attaching it through Documents if they
   want to keep it? **Recommend: yes.** If no: this screen starts storing files and needs its own retention
   rules.
3. Should it stay off by default until a trial on sample documents shows it is accurate enough? **Recommend:
   yes.** If no: it goes live straight away and weak proposals could land in budgets.

## 10. Multi-year budgets: split from the command line and data loader (#1423)

Gives the command line and the starting-data loader the same "one total per category, spread over the years"
split the app already has. The in-app part has shipped.

1. Should the loader file carry the split inside each project's entry, with a separate split option only on the
   budget split command? **Recommend: yes.** It is reviewable and set per project. If no: one split option
   applies to the whole file, which is wrong when projects run different lengths.
2. Should loading again with a different split refuse to overwrite a draft's saved split, and point to the
   budget split command instead? **Recommend: yes.** If no: a reload silently replaces someone's edits.
3. Can the app's spreadsheet import stay per-year with no split option? **Recommend: yes; the app grid already
   splits whole-project drafts. Revisit if operators ask.** If no: the import wizard gains a split step.

## 11. Cost attribution follow-ups (#1362)

Makes sure changing a cost split rule does not rewrite past months, that totals come from one point in time,
and that a rule can never apply money in the wrong currency.

1. Should "Change from date" (applies from a date forward) be the main button, with editing in place only behind
   a warning that past months will change? **Recommend: yes.** If no: editing in place stays the easy path and
   past reports keep changing.
2. Is it acceptable that a cost arriving just after a monthly snapshot is counted in the next snapshot, so
   every total comes from one consistent cut? **Recommend: yes.** If no: snapshots stay mixed, and two reports for
   the same month can disagree.
3. Should a rule that would mix currencies be refused, not just warned about? **Recommend: refuse.** If no: a
   warning can be clicked past, and wrong money stays in the reports.

## 12. Approvals: one shared list of approver roles (#1072)

Mostly tidying behind the scenes: one place defines who can approve, so the approvals page, the spend settings
and the badge counts can't disagree.

1. Can the first item on this ticket (bring expenses, cash advances and customer invoices into the approvals

   close it.** If no: it stays open and the builder re-checks every queue.
2. Should the shared role list live with the other role lists rather than with the permission rules?
   **Recommend: yes.** If no: no change for users, only where the list is kept.
3. Should we delete seven old tests that pin how the approvals page looks, keeping the tests of its behaviour?
   **Recommend: yes.** If no: they keep breaking on harmless layout changes.

## 13. Request review: budget activation and work-order handoff (#980)

Gives the author of a budget draft or work order an in-app "request review" step that shows who it waits on and
since when, so the handoff no longer happens over chat.

1. Should the author be able to name one reviewer, with the whole reviewer group notified by default?
   **Recommend: yes.** If no: either always the whole group (noisy) or always one name (stalls when that person
   is away).
2. Should a "nudge again after some days" button wait for later, with the waiting time shown in the queue?
   **Recommend: yes, later.** If no: we add re-notification now, along with rules to keep it from spamming.
3. Should budgets and work orders ship together in one piece of work, with procurement showing the same status?
   **Recommend: yes.** If no: two releases and two similar screens built separately.

## 14. Tax registers for the monthly returns (#898)

Gives Finance, for a chosen month, output VAT against input VAT, customers' withholding slips checked against
the expected rate, and the withholding we owe on supplier bills, enough to fill the monthly returns.

1. Should the expected withholding rate come from rates an Admin sets in company settings, one per tax article,
   rather than fixed built-in rates? **Recommend: yes, company settings.** If no: fixed rates, and every company
   with a different rate sees false mismatches.
2. Should the VAT register group by tax invoice date, with VAT documents that have no tax invoice yet shown
   under "Awaiting tax invoice"? **Recommend: yes.** If no: grouping by document date can put VAT in a different
   month from the return.
3. Should all three registers ship together? **Recommend: yes; it is a small to medium job.** If no: VAT first,
   with the withholding registers later.
