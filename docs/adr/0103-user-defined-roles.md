# ADR-0103: User-defined roles

**Status:** Proposed for Director and owner review, 2026-11-20
**Related:** #902, #903–#907, ADR-0016, ADR-0019, ADR-0070, ADR-0075

## Context

An organisation needs roles adapted to its work without another enum release. #903 is a historical catalogue, not a current inventory: changes since its snapshot must be inventoried at the target schema head. #904 (OD-ROLE-2) defines assigned projects as the explicit project team, with the named PM always included. `policy.ts` is an affordance projection; the database and server transitions are authoritative. ADR-0075 is proposed and its existing implementation and later decisions must be checked before changes to routing. This ADR proposes decisions for review, not an owner ruling.

## Decision proposed

Use normalized, organisation-owned data, not permissions embedded in JWTs. `roles(id, org_id, name, rank, preset_key, is_system, archived_at)` has unique live names per org; `permission_catalogue(key, module, action, scope_kind)` is versioned in migrations, with separate fine-grained keys for distinct decisions. `role_permissions(org_id, role_id, permission_key, scope)` has one row per grant, `scope` = `organisation` or `assigned_projects`; absent is deny. Composite foreign keys bind role, project and member to the same org. `profiles.role_id` references one role; no per-user overrides in this first release. A project-team table has unique `(org_id, project_id, profile_id)`, and a transactionally maintained PM membership invariant survives a PM change. Team membership does not imply another permission.

Seed one protected Admin role and four editable built-in presets per org, each initially mirroring the current server decisions and the separately preserved FE affordance decisions. Copies are independent custom roles. Protect system role identity, not all its grants: the Admin recovery capability and at least one active administrator are immutable invariants; other preset grants are editable after parity cut-over. Role names are labels, never authority. Archive is refused while assigned; no cascading deletion of audit or assignments. Administrative changes, including rank, memberships, grants, routing and assignment, are audited with actor, time, old and new values and org. Management operations are transactional, privileged, org-scoped and require active authorised administration; self-escalation and cross-org references are refused.

Rank remains a separate ordered authority axis per ADR-0070. Seed the existing order unchanged; use a bounded integer rank with ties allowed for custom roles (strictly greater means outranks; equality never does). The protected Admin is above all custom roles; only an authorised Admin may assign rank, and no one may grant authority at or above their own except the existing Admin peer carve-out. Existing profile-administration floors and approval eligibility floors remain independent checks. An approval grant does not itself confer manager status, rank, budget authority, or a SoD exception. Defaults and exact rank placement for #1407 and #1409 need owner sign-off; neither requested role implies access to overhead or organisation-wide finance.

The JWT identifies the actor; the server resolves active membership, current role and grants from authoritative tables on each transaction. Revocation applies to the next authorised request without token refresh; an already-running transaction retains its database snapshot. Never accept client-supplied org, actor, role, rank, project or amount as authority; derive record context from the persisted row and enforce both old and new scope on moves. Unknown keys, missing context, inactive membership and foreign orgs deny. RLS, security-definer RPCs, triggers and edge/CLI paths use the same permission vocabulary, retain their existing grants and independent lifecycle, ownership, rank, assignment, SoD and column checks. Resolve the caller's organisation-level grants once per statement where possible; use indexed project membership existence checks for row-dependent scope. Benchmark realistic procurement list cardinalities and EXPLAIN (ANALYZE, BUFFERS) against baseline before cut-over; set an owner-approved budget from observed baseline, not an invented threshold. Avoid per-row network calls and do not cache permissions across transactions without revocation guarantees. Fix function `search_path`, minimise EXECUTE grants, and review `role_table_grants` and `pg_policies` at head.

The FE consumes a server-produced permission projection for the real actor, with a separate read-only view-as projection; write decisions remain server enforced. Preserve existing stricter FE behavior initially even where server and UI differ. No client-supplied projection is trusted. Record-specific conditions are evaluated again at mutation time.

Approval routing is a separate narrowing layer over grants and existing domain controls. Proposed matrix rows are org + document type + currency + inclusive lower and exclusive upper amount + project/organisation scope + eligible assigned role or person. Reject overlapping rows for the same matching dimension; use stored numeric amounts and currency, never implicit conversion. Missing, ambiguous, negative or unknown amounts, no matching row, or no eligible approver fail closed with an actionable escalation; no automatic self-approval. Existing explicitly authorised fallback and sole-operator exceptions remain unchanged until separately ruled. The resolver and notifications use the same eligible set and re-evaluate at transition time under the existing domain lock. Changes to the existing fallback, approval floor or currency interpretation require explicit owner decisions; the matrix must not silently change them.

## Migration and proof

1. At a pinned target schema head enumerate `pg_policies`, `pg_proc` definitions and `role_table_grants`, including direct and transitive helpers, triggers, edge functions, CLI, notifications and FE gates; classify each reachable entry and record its independent predicates and test owner in a private inventory. Capture the actual five-preset server and FE outcomes, including intentional differences. Historical counts from #903 are not coverage targets.
2. Write pgTAP characterization against the existing schema first: exercise reachable reads and writes as real authenticated roles, including `USING` and `WITH CHECK`, stored read-back for silent denials, functions, grants, org boundaries, active state, assignments, nulls and SoD. Seed catalogue-derived expected outcomes from observed head, with explicit evidence for every row; no generated expectation may call the new evaluator. Mutation checks must kill removal of a role/scope/SoD guard.
3. Add tables, protected seeds and shadow evaluation without changing authority. Compare old and new results over every inventoried preset × permission × relevant context, including both UI and server baselines; missing mappings and discrepancies block progress. Per-module migration replaces each reachable policy/function and non-SQL consumer while preserving grants and independent predicates. Start with a measured procurement slice, then other project modules, org-wide modules, money/routing and administration; keep each slice reversible and tested. Old and new checks are compared in isolated fixtures, not combined by permissive-policy OR in production.
4. Backfill profile role IDs transactionally and validate counts and org consistency. Keep old enum and column synchronized only through controlled writes during coexistence; reject custom assignment until every consumer is converted. A deployment gate checks the live catalog and source inventory for unclassified consumers, exact parity, hosted grants, tests and procurement performance. Cut over last in one deploy: enable custom assignments and remove enum dependencies only after all checks pass. Rollback before custom assignments restores old readers; after custom roles or edits exist, freeze writes and restore a captured pre-cutover snapshot or use an explicitly reviewed reverse mapping — never silently collapse custom grants into an enum.

## Alternatives and consequences

Embedding grants in JWTs is rejected: edits and revocations would wait for expiry and large matrices bloat tokens. Retaining role-name checks and adding enum values is rejected: custom roles require recurring code changes. Normalized grants add joins, migration and audit complexity; indexes and measured query plans are required. A single rank is useful for hierarchy but is not a substitute for scoped permissions or domain-specific approval authority. The inventory and parity proof, including historically stricter UI paths, are prerequisites, not an assertion that the historical catalogue still describes head.
