# Consumable Usage Standards Implementation Plan (#2577)

## Built on defaults (owner to confirm)

Built on the spec's recommended defaults; none of these is a ruling.
- OD-CUS-1: a standard matches by work unit (case/trim-insensitive) with an optional contract-line code prefix (`boq_items.item_code`); no per-line or per-discipline standard.
- OD-CUS-2: plan figure precedence is consumable plan line, then BoQ allowance, then 0.
- OD-CUS-3: over plan warns and requires a reason (the existing `MRQ_OVER_PLAN_REASON` in `mrq_submit`, unchanged); nothing blocks.
- OD-CUS-4: standards carry a margin % (default 0) applied in the plan.
- OD-CUS-5: standards are managed at stock master-data rank (>= 20); plans are generated and adjusted under the BoQ allowance project rule (Admin/Executive/Finance on any project, a Project Manager on their own).
- OD-CUS-6: plans are snapshots, regenerated only on request, with an out-of-date flag; no ADR written (owner has not confirmed).
- OQ-CUS-1: work unit is free text matched case-insensitively and trimmed; a standard that matches no live line shows "No lines" on the standards screen.
- OQ-CUS-2: standards are not effective-dated; history is in record history.
- OQ-CUS-3: standards apply to the allocated quantity (`work_order_lines.quantity`), not executed quantity.

Decisions the builder made where the spec was silent (also owner to confirm):
- Migration numbers are 1154 (standards + record history), 1155 (plan lines, functions, match counts), 1156 (plan-figure precedence, ships alone); rollbacks under `supabase/migrations/rollback/`.
- An empty plan (a regeneration that matches nothing and keeps no adjusted line) leaves no row, so it cannot be flagged out of date; the "no standard" list is always live. The fingerprint is stored per plan line (as the plan says) rather than in a header table.
- Adjusting or adding a plan line on a Closed or Cancelled work order is refused, the same as generation (FR-CUS-006 names generation only).
- `p_adjusted_qty = null` on `cus_adjust_plan_line` reverts a line to its generated figure (and removes a hand-added line); not in the spec, needed so an adjustment can be undone without regenerating.
- "Matches now" on the standards screen (FR-CUS-004) counts the lines a standard's own rule matches in Draft/Issued work orders (`cus_standard_match_counts`, invoker + RLS); a longer-prefix standard of the same item may still win a line at generation.
- The plan screen also lists items already requested on the work order that have no plan line, with their figure and source (`allowance` or `none`), so "No plan" is visible where it matters.
- The consumable plan section is mounted on `/work-orders/:id` for organisations with the stock module on; the standards screen is `/stock/usage-standards`, reached from the stock section tabs for every role (read-only for those who cannot write).
- `cus_get_plan` returns quantities as decimal strings so the screen never meets a float.
- The 0178 retained-RPC allow-list and its two counts (224 to 226) gained `cus_generate_plan` and `cus_adjust_plan_line`; the isolation denominator gained the two tables and seven definers.

Reuse, don't re-invent: `work_order_lines` (0337), `boq_items` (0250), `stock_items`/`stock_units` (0412), `boq_material_allowances` and its project rule `may_record_project_progress` (0417), `mrq_plan_quantity`/`mrq_plan_for`/`mrq_submit` (1001), `record_history` (0260), the import wizard descriptors (#2530).

## Design summary
- Two new tables: `consumable_usage_standards` (the organisation's standards, soft-archived) and `work_order_consumable_plan_lines` (one row per work order and item: generated qty, optional adjusted qty and reason, basis jsonb, input fingerprint, generated by/at). The only writer of plan lines is a security-definer function; standards are written directly under RLS with column grants, as 0417 does for allowances.
- Pure function `computeConsumablePlan(lines, standards)` in TypeScript mirrors the SQL generation so the screen can preview and the unit test pins the maths (rounded once per item, longest-prefix match). The SQL function is the authority.
- "Out of date" is a fingerprint (hash over the work order's line ids and quantities and the matching active standards) stored at generation and recomputed at read.
- Material requests: the plan figure gains the precedence of FR-CUS-011 and a source; `material_request_lines` gains a `plan_source` column. Over-plan reason behaviour is unchanged (still enforced in `mrq_submit`).
- ADR candidate: "the work-order consumable plan is a stored snapshot, not a live view" (OD-CUS-6), the reason being approvers judge requests against a figure that must not move under them. Write the ADR in the build PR only if the owner confirms.

## Migrations (numbers assigned by the Director; each with a rollback file; RLS + FORCE RLS; `stamp_org_id`)
- **Migration A** `consumable_usage_standards`: table (item_id, work_unit, boq_code_prefix, qty_per_unit numeric(14,6) > 0, margin_pct numeric(5,2) 0..100, archived_at), unique index on (org_id, item_id, lower(btrim(work_unit)), lower(coalesce(boq_code_prefix,''))) where archived_at is null, indexes (org_id, item_id) and (org_id, lower(btrim(work_unit))); `stamp_org_id` trigger; a check function that the item is active and same org (the `boq_allowance_ok` pattern); select for same-org active members; insert/update/delete by the stock-master rank rule; column grants. Rollback: drop table.
- **Migration B** `work_order_consumable_plan_lines`: table (work_order_id, item_id, generated_qty, adjusted_qty, adjust_reason, adjusted_by, adjusted_at, basis jsonb, input_fingerprint text, generated_by, generated_at, updated_at; unique (work_order_id, item_id); check adjusted_qty is null or reason present), FORCE RLS, select only to `authenticated`; functions `cus_plan_fingerprint(work_order_id)`, `cus_generate_plan(work_order_id)` (refuses Closed/Cancelled, project rule, set-based, keeps adjustments), `cus_adjust_plan_line(work_order_id, item_id, adjusted_qty, reason)` (upsert, so it also covers adding an item no standard covers; refuses an archived or other-organisation stock item), `cus_get_plan(work_order_id)` (plan lines + "no standard" lines + out-of-date flag + prior quantity). Rollback: drop functions, table.
- **Migration C** (ships alone, approval path; base it on the 1001 bodies at the then head of `dev`):
  - Today (1001): `mrq_plan_quantity(p_work_order_id uuid, p_item_id uuid) returns numeric`, internal (no client grant); precedence allowance (prorated by `least(wl.quantity / b.quantity, 1)`, rounded 3) else 0; no source. `mrq_submit(p_request_id uuid, p_client_request_id uuid default null)` snapshots `plan_qty` and `prior_qty` per line at submit (confirmed: the `update material_request_lines set plan_qty = v_plan, prior_qty = v_prior` in its loop; no other writer). `mrq_plan_for(uuid, uuid[], uuid) returns table (item_id uuid, plan_qty numeric, prior_qty numeric)`.
  - New precedence: plan line for (work order, item) -> `coalesce(adjusted_qty, generated_qty)`, source `adjusted` if `adjusted_qty` is not null else `standard`; else the unchanged allowance expression, source `allowance` when at least one allowance row joins, else 0 with source `none`.
  - Steps: (1) `alter table material_request_lines add column plan_source text check (plan_source in ('standard','adjusted','allowance','none'))`, nullable; (2) new internal `mrq_plan_figure(p_work_order_id uuid, p_item_id uuid) returns table (plan_qty numeric, plan_source text)` holding the precedence, revoked from every client role like the other internals; (3) `create or replace mrq_plan_quantity` with the same signature, returning `plan_qty` from `mrq_plan_figure` (so any other caller is unchanged); (4) `create or replace mrq_submit` with the same signature: it reads the figure and source from `mrq_plan_figure`, keeps the over-plan test and the `MRQ_OVER_PLAN_REASON` raise byte-for-byte (and its `-- mut:over_plan` tag), and snapshots `plan_source` beside `plan_qty` and `prior_qty`; (5) `mrq_plan_for`: a changed `returns table` cannot be done with `create or replace`, so `drop function public.mrq_plan_for(uuid, uuid[], uuid)`, recreate it with `plan_source text` added, and repeat its grants (revoke from public, anon; grant execute to authenticated).
  - Rollback file: drop `mrq_plan_figure`, drop and recreate `mrq_plan_for` and `create or replace` `mrq_plan_quantity` and `mrq_submit` with the 1001 bodies, drop the `plan_source` column (a snapshot of the source is lost; figures are kept).
- Record history (inside Migration A; mechanism from 0260, usage from 0281): (1) `insert into public.record_history_config (entity_type, table_name, parent_type, parent_col, parent_via, captured, flag_cols, omit_cols)` with entity_type `usage_standard`, table_name `consumable_usage_standards`, parent columns null, and **every** column of the table classified exactly once as captured (`item_id` ref, `work_unit` text, `boq_code_prefix` text, `qty_per_unit` number, `margin_pct` number, `archived_at` timestamp) or omitted (`id`, `org_id`, `created_at`, `updated_at`); (2) `create trigger consumable_usage_standards_zz_record_change after insert or update on public.consumable_usage_standards for each row execute function public.record_change_capture()` (the name must be `<table>_zz_record_change`); (3) `create or replace function public.record_history_visible(...)` re-stating the latest body (0448 at the time of writing; copy the head version) with one added arm `when 'usage_standard' then return exists (select 1 from public.consumable_usage_standards where id = p_entity_id)`, then its revoke/grant lines. `supabase/tests/record_changes_catalog_gate.test.sql` already fails on an unclassified column, a missing trigger or a missing visibility arm, so it proves the registration; its hard-coded `is(count, 17)` becomes 18 with the new entity. The rollback deletes the registry row and the trigger and restores the previous `record_history_visible` body (the 0281 rollback is the pattern). Plan lines are not registered: they carry generated by/at and the adjustment reason, actor and time themselves.
