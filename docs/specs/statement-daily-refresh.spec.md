# #1216 — Daily organisation-local statement refresh and queued manual refresh

**Date:** 2026-10-19 · **Status:** Proposed; owner direction captured below, recommended defaults await sign-off. Docs only; no implementation or release approval.

## Job story and scope

When Finance is reviewing the books, they need to know when saved statements were acquired and be able to request an update without waiting in the browser for ERPNext. Ordinary statements refresh daily at the organisation's midnight, rather than hourly. Admin has the same refresh authority; Executive remains a reader. Invoicing, purchasing and timesheet reconciliation remain hourly. Preserve bounded fast first publication after setup.

Owner authority: issue #1216 brief, 2026-10-19. This proposed amendment changes **only statement cadence and its request/status surface**. It preserves OD-FS-023/024/025's native values, complete catalogue, incremental historical retention, atomic publication, privacy and runtime bounds. It explicitly replaces OD-ERP-023's whole-sweep fast exception with a statement-only fast lane; the other domains remain hourly. It does not modify the five-minute trigger, immediate dispatch or ClickUp.

## Recommended design defaults (proposed, not additional owner rulings)

- **D1 — Midnight means admission:** first available five-minute tick on/after local midnight; not completion at exactly 00:00. Daily work is one successful run per organisation-local calendar day, not a rolling 24-hour timer. Missed days coalesce into one catch-up, not a replay per day.
- **D2 — Success and admission day:** persist the local day/timezone at admission. Advance the completed-day marker only with atomic publication. A manual run satisfies the daily obligation for its admission day. A run spanning midnight does not consume the next day's obligation.
- **D3 — Requests:** one outstanding manual request per org, including one being processed. Repeated requests return the same receipt and never move its timestamp. A request arriving during an automatic run is a single follow-up, because that run may already have acquired its reports. A request already attached to a run coalesces into that run. Five minutes between newly accepted manual requests, even if the previous run finished sooner. No requester identity needs to be stored.
- **D4 — Progress/recovery:** daily/manual runs may continue on five-minute statement-only ticks for six hours from their first admission; after that they resume hourly without resetting their window or discarding staged progress. Setup keeps the existing six-hour activation/matching-batch first-publication rules. For daily/manual runs, clicks, errors, retries, context changes and rolling midnight do not renew the active run's fast-window start; the first-publication lane retains the shipped activation/recent-batch semantics.
- **D5 — Refresh scope:** automatic and manual refresh both use the existing incremental plan, not an unconditional historical refetch. Dirty dates do not independently start a statement run. A change observed by the hourly ledger stage is consumed by the next admitted daily/manual run (or a later batch if it exceeds the active batch cutoff). This intentionally changes DD-FS-REFRESH-1's next-tick timing, not its durable invalidation or dependency horizon.
- **D6 — Timezone changes/rollout:** use `organizations.default_timezone`, never viewer/device timezone. A changed organisation timezone makes the next tick eligible for one catch-up in that timezone; its completion establishes the new day marker. On rollout, initialise an absent schedule lazily from an exact-current-binding native publication's timestamp, avoiding a redundant same-day refresh. Older/missing matching publications remain due. A future activation cannot grant fast first-publication progress.
- **D7 — UX:** show organisation timezone and daily cadence to company readers; preserve the existing publication timestamp and per-side acquisition/capture dates. Finance/Admin get a quiet text-styled **Refresh now** action above the report controls, including before first publication when the connection is eligible. Submission shows **Queuing refresh…**; committed request shows **Refresh queued**; an admitted run shows **Refreshing saved statements…**. These are not the existing **Retry** (reload saved data) operation. Executive sees status but no write action. View-as is read-only for this new write.

## Requirements (EARS)

| ID | Requirement |
|---|---|
| FR-001 | When an eligible organisation enters a new local calendar day, the sweep shall admit one daily statement refresh on its next available tick unless that day's obligation is already completed or covered by an active run. |
| FR-002 | While a daily/manual batch is incomplete or has failed, the system shall retain the last complete saved catalogue, its publication/acquisition timestamps and the outstanding demand; only successful atomic publication shall acknowledge the admitted day and captured request. |
| FR-003 | When a binding lacks its first exact-current-context native publication, the statement lane shall preserve the existing bounded activation/recent-batch fast window and hourly recovery outside it. |
| FR-004 | While no statement work is due, the hourly sweep shall skip native statement metadata/report acquisition, attempt admission and batch/publication mutations; it shall continue ordinary invoicing, purchasing, ledger/accounting and timesheet work hourly. Between hourly windows only due statement work shall execute. |
| FR-005 | When an active own-org Finance/Admin requests refresh, a server-enforced RPC shall queue demand for that org without accepting a client org, company, role, period, URL or source override and without making an ERP call. Other actors shall be refused. |
| FR-006 | When a request is already outstanding, the RPC shall return its original receipt; when no request is outstanding but the five-minute acceptance cooldown has not elapsed, it shall return a retry time without inserting demand. |
| FR-007 | When publication completes, it shall clear only the request captured at that run's admission, retain a later request, and commit schedule acknowledgement in the same transaction as the full catalogue replacement. |
| FR-008 | While company readers are authorised, a narrow read surface shall expose connection eligibility, queued/running state, cooldown expiry, organisation timezone and last successful publication, without exposing internal binding/context/request storage. |
| FR-009 | While the real active identity permits refresh and no view-as is active, the statements page shall show the Refresh now link-styled action only to Finance/Admin, and shall prevent duplicate submission while pending, queued or cooling down. |
| FR-010 | When request/status calls fail, the UI shall preserve saved statements and selections, show a persistent local retryable error, and shall not claim the refresh was queued or completed without server confirmation. |
| FR-011 | When a request is accepted or a status poll observes publication, the UI shall update status and invalidate saved statement reads for the same authorised identity only, without changing source financial values or fabricating acquisition dates. |
| FR-012 | While viewing the company statements page, readers shall see daily-cadence/timezone context, honest publication/capture provenance and distinguish queued/running/read-retry states in both supported locales and at phone/desktop widths. |
| NFR-001 | The statement lane shall retain the existing lease fence, seven-second segment/five-second request limits and remaining-tick budget, use serial native acquisition, and shall not extend them for manual work. |
| NFR-002 | The new business state shall have an `org_id` key, forced RLS, least-privilege grants, fixed-search-path write functions, reversible migrations and indexed bounded lookups; authorised RPCs shall derive org/role/member state server-side. |
| NFR-003 | The implementation shall use the existing repository/DAL/cache and permission seams, paginate org work reads in batches of at most 100, use no per-user cron, no browser ERP call and no new external dependency. |
| NFR-004 | While refresh is queued/running, status polling shall be at most once per 15 seconds per mounted query key, stop when idle/unmounted/unauthorised/hidden, and never poll ERP. Live feedback shall be keyboard accessible, non-colour-only and announced politely; errors use an alert. |

## Non-goals

No synchronous browser ERP operation, configurable schedule UI, per-report queues, historical-force-refresh option, new accounting calculation, monetary transformation, unrelated write-authority changes, cron replacement, production deployment or broad source refactor. Legacy chart/ledger feeds still run hourly and may create dirty markers; that is not a native statement refresh. A queued request promises eventual bounded-worker processing, not an exact completion time or an ERP-wide transactionally consistent snapshot.

## OPEN QUESTIONS — owner decisions requested, recommended defaults already specified

1. **OQ-1: Does “midnight” mean start or finish?** Recommend D1: start on the first available five-minute tick after organisation midnight; completion depends on catalogue size and ERP availability.
2. **OQ-2: Is a successful manual refresh sufficient for that local day's scheduled refresh?** Recommend D2: yes; use admission day, so spanning midnight cannot suppress the following day's work.
3. **OQ-3: What happens if Refresh now is clicked during an automatic refresh?** Recommend D3: queue one follow-up; an already captured manual request coalesces. Enforce one outstanding manual request plus a five-minute acceptance cooldown.
4. **OQ-4: May daily/manual work use bounded fast continuation?** Recommend D4: five-minute statement-only segments for six hours, then hourly recovery. Never accelerate invoicing/purchasing/timesheet stages.
5. **OQ-5: Should dirty historical changes trigger extra runs?** Recommend D5: no; consume them at the next daily/manual admission, preserve all later dirty revisions. Manual refresh uses the same incremental scope, not a forced whole-history reread.
6. **OQ-6: How should timezone changes and initial rollout behave?** Recommend D6: one catch-up after timezone change; exact-current native publication today seeds rollout's day marker lazily.

These are approval choices within the supplied job, not missing ACs. This specification has complete proposed acceptance criteria but is not owner-signed; implementation starts only after the Director obtains sign-off or confirms explicit approval of these defaults.
