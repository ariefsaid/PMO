# Installable PWA with offline reads — spec (#718)

**Status:** proposed, 2026-09-29. **Authority:** OD-CR-12 (`docs/decisions.md` / `docs/backlog.md`: OD-CR-6 amended, PWA un-parks — installable + offline **reads**, **no offline writes**; native mobile, in-house chat, field photos/forms stay parked), ADR-0016 (`can()` is UX, RLS is authority), ADR-0017 (repository seam), `DESIGN.md`, `docs/qa-portfolio.md`. **Executor:** factory slice (`fe_builder` / `fe_reviewer`) after plan; security review focuses on cache contents across sign-out and user switch.

## Job story

When I am on site or on a weak connection, I want PMO installed on my phone and able to show the records I last looked at, so I can answer a question without a signal — without ever seeing someone else's data, and without believing a stale number is live.

## Scope

In: web app manifest + icons (installable on Android, iOS "Add to Home Screen", desktop Chromium); service worker (app shell + Supabase REST GET reads); offline/online status UI; write blocking while offline; cache purge on sign-out / identity change; in-app update prompt; EN + Bahasa copy.

Out (explicit): offline writes, queued or replayed mutations, background sync; native app; push notifications; in-house chat and field photos/forms; offline file/document bodies (storage downloads and signed URLs); offline sign-in (an installed app with no valid saved session cannot log in offline); caching RPC (`POST`) reads; an in-app "Install" button (browser-native install UI only, v1); precise freshness guarantees (this is best-effort recent-view cache, not a sync engine).

## What the code looks like today (design inputs)

- No manifest, no service worker, no PWA dependency. `index.html` links only `/vite.svg`; `public/` holds `_redirects` (SPA fallback), `fonts/`, `locales/{en,id}/common.json`. Hosting is Cloudflare Pages (static; no `_headers`, no CSP in repo).
- Reads: repositories delegate to `src/lib/db/*`, which call the singleton `supabase` client (`src/lib/supabase/client.ts`) — PostgREST `GET {backend}/rest/v1/<table>?<filters>` with `Authorization: Bearer <user JWT>` + `apikey`. A minority of reads are `rpc()` `POST`s (usage summaries, `get_project_drawdown`); these are not cached in v1.
- react-query singleton (`src/lib/queryClient.ts`): `staleTime 30s`, `gcTime 5m`, `retry 1`, default `networkMode: 'online'` — **offline, queries pause forever instead of calling fetch**, so a service worker alone would never be asked. Mutations default to `networkMode: 'online'` — **offline, mutations pause and replay on reconnect, i.e. a hidden write queue**. Both defaults must change.
- `AuthProvider` already calls `queryClient.clear()` when the session identity changes (covers explicit sign-out, other-tab sign-out, token expiry, user switch). `signOut()` calls `supabase.auth.signOut()`, which needs the network.
- i18n loads `fetch('/locales/<lng>/<ns>.json')` at runtime — the locale files are shell, not bundle, and must be cached or Bahasa/English cold-start offline renders keys.
- Route chunks are hashed lazy imports; `chunkReload.ts` reloads once on a stale-chunk 404.
- `classifyMutationError` has no network-failure class (falls to generic "Update failed").
- Impersonation ("view as") is client-only and does not change the JWT — it does not change cache scope.
- e2e runs against `npm run dev` (port 3000); a service worker must **not** register there (or in Vitest).

## Design decisions

1. **Hand-written service worker; no new dependency.** A ~150-line classic-script SW, plus a small in-repo Vite plugin that (a) emits `sw.js` at the site root with a build id (existing `__GIT_SHA__`) so every deploy changes the bytes and triggers the update path, and (b) injects the precache list (`index.html`, entry JS/CSS, fonts, both `locales/*/common.json`) from the bundle. Cache policy is pure functions in `src/lib/pwa/swPolicy.ts`, imported by both the SW entry and unit tests (the SW is built as a second IIFE entry; the plugin owns this). **Alternative — `vite-plugin-pwa` (Workbox): rejected for v1** because it adds a Workbox tree of transitive dependencies to a public supply chain to solve a precache list and two runtime routes, and its default runtime caching keys on URL alone (the wrong default here; see 4). **Flag: adding `vite-plugin-pwa` is an owner/Director decision** if the hand-written precache proves fragile.
2. **Registration:** `src/lib/pwa/registerServiceWorker.ts`, called from `index.tsx`, registers `/sw.js` (scope `/`) only when `import.meta.env.PROD` and `'serviceWorker' in navigator`. Never in dev or Vitest.
3. **App shell strategy.** Navigations: network-first with a short timeout (3s), fall back to the cached `/index.html` (SPA; deep links work offline). `/assets/*`, `/fonts/*`, `/locales/*`: cache-first into a build-versioned cache `pmo-shell-<buildId>`; entries not in the precache list (lazy route chunks) are added on first fetch, so "recently viewed" routes work offline. Old `pmo-shell-*` caches are deleted on `activate`.
4. **Data strategy — network-first, cache fallback, per-user cache.**
   - **Cacheable** = `GET` to `<backend>/rest/v1/<table>` where `<table>` is on a **fail-closed allow-list** in `swPolicy.ts`, and the request carries a user JWT (not the bare anon key), and no `Range` header. Initial allow-list: the tables read by Projects, Sales Pipeline, Procurement, Companies, Contacts, Meetings, My Tasks and their record pages, plus the `profiles`/membership reads the shell needs to render. **Excluded by construction:** everything not listed (a new table is uncached until someone adds it and its test), `agent_*`, audit, integration/credential and operator tables, notifications, all `/auth/v1`, `/storage/v1`, `/functions/v1`, realtime, and every non-GET. Money-ledger tables (invoices, payments, revenue) are excluded in v1 (see open question 1).
   - **Scope key.** The SW derives `sub` from the request's own `Authorization` JWT (decode only, no verification — used for partitioning, never for trust) and uses `pmo-data-v1-<sha256(sub)[0..16]>` as the cache name. Identity comes from the request, so there is no dependence on a page-to-worker message arriving first. Invariant: **at most one `pmo-data-*` cache exists**; before any write to a scope, every other `pmo-data-*` cache is deleted. An offline read whose `sub` differs from the existing cache is a miss.
   - **Stored key is synthetic.** Entries are stored under `new Request('/__pmo-cache/' + sha256(url + accept + prefer))` — a header-less request, so **`Authorization` and `apikey` are never persisted** (the Cache API stores request headers with the key otherwise; `cache.keys()` would hand the next user of the device a live bearer token). `Accept` (single-object vs array) and `Prefer` (count) are in the hash because they change the response shape.
   - **Stored value** = the `200` JSON response, re-wrapped with `x-pmo-cached-at` (epoch ms). Not stored: non-200, non-JSON, > 1 MB body, or bearing `Set-Cookie`.
   - **Bounds:** max 150 entries, 1 MB per entry, and 25 MB total (on insert, evict oldest by `x-pmo-cached-at` until under both caps); a read older than 7 days is treated as a miss and deleted. Network-first waits up to 8 s for data before falling back to cache.
5. **Purge is page-driven and does not need the worker.** `src/lib/pwa/purgeOfflineCaches.ts` deletes every `pmo-data-*` cache directly through `window.caches` (the Cache API is available to pages). `AuthProvider` calls it (a) at the top of `signOut()` **before** `supabase.auth.signOut()`, so it works offline and cannot be skipped by a failed network call, and (b) in `apply()` beside the existing `queryClient.clear()` on identity change, and (c) when the profile's `org_id` changes for the same user. Shell caches hold no user data and survive sign-out (a signed-out app still opens `/login`).
6. **Offline state.** `useOnlineStatus()` = `navigator.onLine` + `online`/`offline` events, mirrored into react-query's `onlineManager`. On regain, stale queries refetch. The SW posts `{type:'served-from-cache', cachedAt}` to clients on each cache-served response; the page tracks the **oldest** `cachedAt` served since going offline and shows that (conservative: the stalest data visible). If nothing was served from cache the notice reads "Offline" without a time.
7. **`OfflineNotice`** — one persistent strip at the top of the shell `main` (the slot `AppShell` already provides as `banner`, alongside the impersonation banner), `role="status"` (polite live region), visible text (never colour alone), warning AA text tokens from `DESIGN.md` (not the raw `--warning`), and a brief "Back online" confirmation on regain. Copy keys under `pwa.*` in `public/locales/{en,id}/common.json` (enforced by `npm run check:i18n`). Time is formatted with the app's locale-aware date-time formatter, not a hand-rolled one.
8. **Writes offline — blocked, never queued, three layers:**
   1. *Choke point (authoritative).* A `fetch` wrapper installed via the supabase client's `global.fetch` rejects any non-`GET` request to the backend while `navigator.onLine === false` with a typed `OfflineError` **before** it leaves the app (covers repositories, RPC, edge functions, storage uploads, the agent panel). `classifyMutationError` gets an `OFFLINE` class → headline "You're offline", detail "This change needs a connection. Nothing was saved." (Bahasa equivalent).
   2. *Affordances.* Shared write surfaces (`EntityFormModal` submit, `ConfirmDialog` confirm, `RecordActionZone` actions, transition buttons, create verbs) read `useOnlineStatus()` and render `disabled` + `aria-describedby` pointing at a visible "Needs a connection" reason. Roles still gate first (`can()`); offline never *grants*.
   3. *No hidden queue.* `queryClient` mutations use `networkMode: 'always'` (fire immediately, fail through layer 1) so react-query never pauses and replays a write on reconnect; queries use `networkMode: 'offlineFirst'` so `queryFn` runs and the SW can answer.
9. **Update flow.** No automatic `skipWaiting`. When `registration.waiting` appears (or `updatefound` → `installed` with an existing controller), the page shows a toast/notice "A new version is available" with a **Reload** action; activation happens only on that click (`postMessage({type:'skip-waiting'})` → `controllerchange` → `location.reload()`), so an in-progress form is never yanked. Until then the old shell and its old chunks stay consistent in the old versioned cache (this also prevents `chunkReload`'s stale-manifest 404). The page checks for an update on load and on `visibilitychange` → visible, at most once per 60 minutes.
10. **Installability.** `public/manifest.webmanifest`: `name` "PMO Portal", `short_name` "PMO", `start_url` `/`, `scope` `/`, `display` `standalone`, `theme_color`/`background_color` = the `DESIGN.md` canvas token (light), icons 192 + 512 (`any`) + 512 (`maskable`, safe-zone padded) as PNG under `public/icons/`. `index.html` gains `<link rel="manifest">`, `<meta name="theme-color">` (light + `media="(prefers-color-scheme: dark)"` variants), `<link rel="apple-touch-icon">` (180 px PNG — iOS ignores manifest icons), `apple-mobile-web-app-capable`/title metas, and drops the `vite.svg` favicon. Icon artwork: generated monogram from `DESIGN.md` tokens, owner sign-off before release (open question 3). Cloudflare Pages serves `sw.js` and the manifest as files ahead of the `_redirects` SPA rule; `sw.js` must not be served with a long `Cache-Control` (verified post-deploy, see risks).

## Functional requirements (EARS)

- **FR-PWA-001:** The application shall publish a valid web app manifest with the required name, start URL, scope, standalone display, theme/background colours, and 192 px, 512 px and maskable 512 px PNG icons, linked from `index.html`.
- **FR-PWA-002:** Where the browser supports service workers and the build is a production build, the application shall register a root-scoped service worker after load; it shall not register in development or test builds.
- **FR-PWA-003:** When the app is loaded again while offline after at least one online visit, the service worker shall serve the app shell (including deep links, and the active locale file) from cache.
- **FR-PWA-004:** When an allow-listed Supabase REST `GET` succeeds for a signed-in user, the service worker shall store the response in that user's cache; when that request later fails at the network, it shall answer from that cache.
- **FR-PWA-005:** The service worker shall store cached data under a header-less synthetic key such that no `Authorization` or `apikey` value is ever written to any cache.
- **FR-PWA-006:** While any `pmo-data-*` cache exists for a different user than the requester, the service worker shall delete it before writing, and shall treat the requester's read as a cache miss.
- **FR-PWA-007:** When the user signs out — including when the network call fails or the device is offline — the application shall delete every `pmo-data-*` cache before the sign-out call is made.
- **FR-PWA-008:** When the session identity or the profile's organisation changes without an explicit sign-out (expiry, other tab, user switch), the application shall delete every `pmo-data-*` cache.
- **FR-PWA-009:** The service worker shall never cache responses outside the allow-list, non-`GET` requests, non-200 or non-JSON responses, responses over 1 MB, or requests without a user JWT; and shall bound the data cache to 150 entries and 25 MB total, evicting oldest first, and treat entries older than 7 days as missing.
- **FR-PWA-010:** While the device is offline, the application shall show a persistent, screen-reader-announced notice stating that saved data is being shown and the timestamp of the oldest cache-served data since going offline.
- **FR-PWA-011:** When connectivity returns, the application shall refetch stale queries and replace the offline notice with a brief "Back online" confirmation.
- **FR-PWA-012:** While offline, when any write is attempted through the backend client, the application shall reject it before it is sent, show a classified "You're offline / nothing was saved" message, and shall not retain the request for later replay.
- **FR-PWA-013:** While offline, the shared write affordances shall be disabled with a visible, programmatically associated reason; the role gate shall continue to apply first.
- **FR-PWA-014:** When a new service worker version is installed, the application shall offer a Reload action and shall activate the new version only when the user chooses it.
- **FR-PWA-015:** When activated, a new service worker version shall delete superseded shell caches; the current user's data cache shall survive an update.
- **FR-PWA-016:** All new user-visible strings shall exist in English and Bahasa Indonesia.

## Non-functional requirements

- **NFR-PWA-SEC-001 (no cross-user / cross-org data):** after sign-out, user switch, or org change, no earlier user's API response is retrievable through the Cache API or served to the app. Verified by test, plus a mutation check (drop the purge / drop the scope check → the test must go red).
- **NFR-PWA-SEC-002 (nothing readable by the next user):** an enumeration of every cache after online use lists no request carrying an `Authorization` or `apikey` header; after sign-out, no `pmo-data-*` cache exists. The worker never logs headers or bodies. (Residual: a device user with DevTools *while a session is live* can read that session's own cache — same exposure as the live app; documented, not mitigable in-app.)
- **NFR-PWA-SIZE-001:** data cache ≤ 25 MB / 150 entries; shell cache ≤ the build's precache list plus visited lazy chunks; no unbounded growth across deploys (old versioned caches deleted).
- **NFR-PWA-UPD-001:** an open tab is never force-reloaded; a stale shell is not served indefinitely (update check ≤ hourly and on foreground; prompt persists until acted on).
- **NFR-PWA-A11Y-001:** offline notice and update prompt are WCAG 2.2 AA: `role="status"`, ≥ 4.5:1 text, not colour-only, keyboard-reachable Reload, reflows at 390 px with no horizontal scroll, disabled controls keep an accessible name + reason.
- **NFR-PWA-I18N-001:** EN + ID keys present and `check:i18n`-clean; offline time formatted by the active locale.
- **NFR-PWA-PERF-001:** the SW never blocks a navigation for more than the 3 s network-first timeout; first-load JS of the app is not increased beyond the ~2 KB registration module.

## Risks and open questions

1. **Which entities are readable offline, and do stale money figures matter? (owner)** Default: the allow-list above; money-ledger tables (invoices, payments, revenue) excluded in v1; amounts on cached project/procurement records show under the saved-at notice. Widening is a one-line allow-list + test change.
2. **`vite-plugin-pwa` instead of the hand-written worker? (Director/owner, new dependency).** Default: hand-written (design decision 1). Revisit only if the precache injection needs more than ~30 lines of plugin.
3. **Icon artwork.** No brand mark exists (`vite.svg` is the template favicon). Default: generated monogram from `DESIGN.md` tokens; owner reviews before release. Does not block the build.
4. **`navigator.onLine` is unreliable on captive/lossy networks.** A request that times out online falls back to cache via network-first (3 s for navigations; 8 s for data) and the SW's `served-from-cache` message drives the notice even when `onLine` is true; writes on lie-fi fail through the normal error path (no data loss, nothing queued). Default accepted; no further work.
5. **Org change for a live session.** If a user's `org_id` can never change without a new session, FR-PWA-008's org clause is redundant but harmless. Default: keep it (one comparison).
6. **Shared-device residue after a hard crash.** If the browser is killed before the purge completes, the cache survives until the next app start; the scope check (FR-PWA-006) ensures another user still cannot be served it, and the next identity change deletes it. Default accepted; documented.
7. **`sw.js` caching at the host.** A long `Cache-Control` on `sw.js` would defeat the update flow. Default: Cloudflare Pages' default for non-hashed files (revalidate); verify with a response-header check on the first deploy that ships this (deploy itself is owner-gated per CLAUDE.md, not part of this issue).
8. **CI cost.** The `pwa` lane needs a production build + preview server in the e2e job. Default: one extra Playwright project, run only in the on-demand/promote e2e lane (CI fair-use: once per PR).

## Boundaries

No schema, RLS, or migration change. No change to auth flows, roles, or `can()` semantics. No new runtime dependency (the worker, plugin, and registration are in-repo). Existing e2e specs keep running against the dev server with no worker registered. Each `AC-PWA-###` has exactly one owning layer; the e2e rows do not duplicate what the unit rows prove.
