## Exact rehearsal steps

1. In PMO, Admin creates a synthetic delivery project `PPNC rehearsal`. Finance/Admin uses the
   contract editor: **10,000,000 IDR exclusive**, rate **12**, base **11/12**, **Subject to VAT on**.
   Confirm those project facts and no existing invoices.
2. Create an Issued synthetic work order on it: **5,000,000 IDR exclusive**, same rate/base, with
   the required value/issue witnesses. No other invoice or live claim bills the order. This permits
   both tested amounts without moving its ceiling during correction.
3. Finance/Admin author A chooses **Invoice this work order**, qty **1**, rate **1,200,000**, valid
   sales item; raise the Draft normally. Record original PMO UUID, ERP name and create intent.
   Finance/Admin B, outside its author set, submits it in PMO. No receipt. Read original-submitted:
   ERP docstatus **1**, net **1,200,000**, tax **132,000**, gross/outstanding **1,332,000**. PMO list,
   mirror, project revenue/AR and work-order billing must agree with the original-submitted row below.
4. A uses the existing PMO **Cancel invoice** action and confirmation, **not amend**. Wait for its
   cancellation command to settle and both ERP/PMO cancellation to be confirmed. Read original-
   cancelled: ERP docstatus **2**, original taxes/amounts unchanged; original PMO mirror Cancelled.
   Project revenue/AR and work-order invoiced/pending become **0**, remaining **5,000,000**. Record
   the distinct cancellation intent; uncertain cancellation is STOP/recovery, not permission to re-issue.
5. A chooses the same normal **Invoice this work order** create path for corrected qty **1**, rate
   **2,400,000**, same customer/project/work order. It is a **new create intent and new PMO UUID**,
   and returns a **different ERP name**. Do not send `verb:amend`, reuse the old UUID, supply old tax
   rows or demand `amended_from`. Reuse the new create intent only for retries of this same create.
6. Read replacement-draft using original and new UUIDs/names. Original remains docstatus **2** with
   tax **132,000**/gross **1,332,000**. NEW ERP invoice is docstatus **0**, net **2,400,000**, fresh
   effective-11% row, tax **264,000**, gross **2,664,000**, no amended-from link. New PMO mirror is
   Draft; AR/revenue **0**; work-order pending **2,400,000**, invoiced **0**, remaining **2,600,000**.
7. B submits the NEW invoice in PMO through normal approval; never auto-submit it or use A as its
   approver. Fresh full GET after submit is mandatory: the PUT response can have stale derived
   outstanding/status. NEW ERP docstatus **1**, outstanding **2,664,000**; new PMO Unpaid mirror
   has gross/tax **2,664,000/264,000**, inclusive mirror treatment. Project revenue **2,400,000**,
   open AR **2,664,000**, active invoice count **1**; work-order invoiced **2,400,000**, pending **0**,
   remaining **2,600,000**. The original contributes nothing to active figures.
8. Observe the **rendered** invoice list, Revenue by Project row and project's work-order billing
   at each phase, alongside backend reads. The list retains a separately identifiable Cancelled
   historical row; its active figures reflect only the new invoice, not old+new. No ERPNext Desk
   tax editing, manual mirror edits or source-code patching to produce a passing screenshot.
9. Independent unlock rehearsal, **only after 0282 is implemented**: cancel the new invoice in PMO,
   wait for settlement, read every project invoice Cancelled and every associated command terminal.
   Snapshot `all-cancelled`, then Finance/Admin switches the flag off and snapshot `flag-changed`:
   cancelled amounts/taxes/identities must match exactly, with one history diff
   `{subject_to_vat:{old:true,new:false}}`. Create and B-submit a fresh invoice normally, now untaxed;
   capture `next-invoice` with that fresh UUID/name as the new pair. It relocks the editor. Native
   equivalent is proved by pgTAP without switching this org's ownership in the rehearsal. Coretax
   replacement remains manual; the new invoice's e-Faktur number uses #893's existing fields.

## Exact REST source reads

Authenticated local GETs, names percent-encoded as individual path segments (`quote(name, safe='')`):

```text
GET http://localhost:8080/api/method/frappe.utils.change_log.get_versions
GET http://localhost:8080/api/resource/Sales%20Invoice/{encoded-original-name}
GET http://localhost:8080/api/resource/Sales%20Invoice/{encoded-new-name}
```

The runtime names come from PMO responses, never a guessed numbering suffix. Full documents must
include `taxes[]` (`charge_type`, `account_head`, `rate`, `tax_amount`,
`tax_amount_after_discount_amount`, `total`, `included_in_print_rate`) plus `net_total`,
`total_taxes_and_charges`, `grand_total`, `rounded_total`, `outstanding_amount`, `docstatus`,
`amended_from`, `currency`, `items[].net_amount`. A list GET does not expose child tax rows.
The helper reads versions plus these full documents; it does not create/cancel/submit anything.

Loopback PMO PostgREST `/rest/v1/` GETs, parameters URL-encoded by the helper:

| Resource | Filters | Selected facts |
|---|---|---|
| `projects` | `id=eq.` + project UUID | `subject_to_vat,tax_rate,tax_base_numerator,tax_base_denominator` |
| `sales_invoices` (two independent reads) | `id=eq.` + original UUID; `id=eq.` + new UUID | `id,si_number,status,pmo_native,amount,tax_amount,tax_treatment,currency,erp_docstatus,erp_outstanding_amount,erp_amended_from,erp_cancelled_at,work_order_id` |
| `sales_invoices` | `project_id=eq.` + project UUID, all statuses | `id,status,pmo_native,erp_docstatus,si_number,amount,tax_amount,tax_treatment` |
| `progress_claims` | `project_id=eq.` + project UUID | `id,kind` for pre-mirror command association |
| `sales_invoices` | same project; `status=in.(Submitted,Unpaid,Paid)` | `id,status,currency,erp_outstanding_amount` |
| `sales_invoice_work_billed` | same project/status filters | `id,status,currency,net,recovery,is_down_payment` |
| `work_order_billing` | `work_order_id=eq.` + work-order UUID | `order_net,invoiced,pending,remaining,figures_complete,line_count,currency` |
| `external_command_outbox` | `domain=eq.revenue`; each original/new `pmo_record_id` | `operation,state` |
| `external_command_outbox` | same domain; `payload->>erp_doc_kind=eq.sales-invoice`; project payload OR project invoice/claim ids | `operation,state` for every associated command |
| `record_changes` | `entity_type=eq.project`; `entity_id=eq.` + UUID; `changes=cs.` + JSON `{"subject_to_vat":{}}` | `seq,created_at,changes` |

Command association uses case-insensitive project matching plus all same-project invoice/claim ids,
including commands omitting projectId. The helper refuses reads reaching the 1000-row REST cap;
a larger fixture needs pagination before asserting “all”. No supersession lineage is expected:
these are two normal invoices, not a same-record amendment.

`getRevenueByProject` in `src/lib/db/revenue.ts` is a paged FE aggregate, not an RPC. For this fixture,
sum submitted outstanding sources for AR; net+recovery on non-down-payment billed rows for revenue.
Compare independently with the rendered row. Work-order **billing** drawdown is net-of-tax.
`get_project_drawdown` is contract-to-work-orders, so it must not change just because an invoice
changes. Never expect gross invoice money in both views.
