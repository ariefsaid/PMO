## 2. Detailed Findings with Primary Citations

### 2.1 API Protocols, Endpoints, and Deprecation Timeline

Odoo has transitioned its external integration architecture from legacy remote procedure calls (XML-RPC and JSON-RPC) to a clean, RESTful JSON RPC endpoint dubbed **JSON-2 API**.

#### The JSON-2 Protocol Specification
* **Endpoint Pattern:** `POST /json/2/{model}/{method}`
  * Examples: `POST /json/2/res.partner/search_read`, `POST /json/2/purchase.order/action_confirm`, `POST /json/2/account.move/create`.
* **Headers:**
  * `Authorization: bearer <API_KEY>` (or `curl --oauth2-bearer $API_KEY`).
  * `Content-Type: application/json; charset=utf-8`.
  * `X-Odoo-Database: <database_name>` (mandatory when multiple databases exist on the host and the `dbfilter` does not isolate the tenant by host).
  * `User-Agent: <software_name> <client_version>` (recommended by vendor).
* **Payload Structure:**
  A single JSON object passing keyword parameters matching the target ORM method:
  ```json
  {
    "context": {"lang": "en_US"},
    "domain": [["is_company", "=", true]],
    "fields": ["name", "email", "vat"]
  }
  ```
  For record-level methods (decorated with `@api.multi` or operating on existing IDs), the record IDs are passed in the `"ids"` array or positional parameters:
  ```json
  {
    "ids": [42],
    "context": {}
  }
  ```
* **Transaction Semantics:**
  * Every HTTP call to `/json/2/...` runs in its **own isolated SQL transaction**.
  * Chaining multiple calls inside a single database transaction over the wire is not supported.
  * To guarantee atomicity across related mutations (such as validating an order and creating lines), callers must invoke a compound method (e.g., `action_confirm` or `search_read`) rather than discrete `search` followed by `read`.
* **Responses & Error Serialization:**
  * Success returns HTTP `200 OK` with the JSON-serialized return value.
  * Errors return HTTP `4xx` or `5xx` with a JSON payload detailing the Python exception: `name`, `message`, `arguments`, `context`, and server traceback (`debug`).
* *Primary Source:* [External JSON-2 API — Odoo Master Documentation](https://www.odoo.com/documentation/master/developer/reference/external_api.html).

#### Deprecation Timeline for Legacy RPC
Odoo has formally established the end-of-life schedule for `/xmlrpc`, `/xmlrpc/2`, and `/jsonrpc`:
1. **Database Service (`/xmlrpc/2/db`):**
   * **Removed in Odoo 20 (Fall 2026)** and Odoo Online 19.1 (Winter 2025).
   * Database management operations (create, drop, backup, restore) are no longer exposed over RPC; they are routed strictly through `/web/database/...` HTTP controllers.
2. **Common & Object Services (`/xmlrpc/2/common`, `/xmlrpc/2/object`, `/jsonrpc`):**
   * **Scheduled for full removal in Odoo 22 (Fall 2028)** and Odoo Online 21.1 (Winter 2027).
   * Web controllers decorated with `@route(type='jsonrpc')` (internal client controllers) remain supported and are not subject to this deprecation.
* *Architectural Verdict for PMO Adapter (ADR-0055):* The PMO Odoo adapter should speak the **JSON-2 API natively**. This eliminates XML-RPC payload overhead, uses standard HTTP Bearer tokens, and guarantees compatibility beyond the Odoo 22 deprecation horizon.
* *Primary Source:* [Odoo RPC Deprecation Section](https://www.odoo.com/documentation/master/developer/reference/external_api.html#migrating-from-xml-rpc-json-rpc).

### 2.2 Authentication & Secret Management

Odoo uses **Developer API Keys** (`res.users.apikeys`) as the standard authentication mechanism for external services, completely superseding user password transmission.

#### Key Characteristics
* **Format:** Cryptographically secure 160-bit pseudo-random token displayed once upon generation.
* **Maximum Lifespan:** Enforced maximum duration of **3 months** (90 days). Odoo does not permit non-expiring API keys. Automated key rotation is mandatory for production adapters.
* **Scope:** Scoped keys restrict endpoints. For external API integrations, keys use the `rpc` scope (or unscoped `null`).
* *Primary Source:* [Odoo API Keys Configuration](https://www.odoo.com/documentation/master/developer/reference/external_api.html#api-keys).

#### Manual vs. Programmatic Key Management
* **Manual Generation:** Generated in the Odoo Web UI under *Preferences ‣ Account Security ‣ Developer API Keys ‣ New API Key*. Requires user password confirmation.
* **Programmatic Lifecycle API:**
  * Odoo exposes RPC endpoints on `res.users.apikeys`:
    * `generate(key, scope, name, expiration_date)`: Generates a new API key authenticated by an existing valid key.
    * `revoke(key)`: Immediately invalidates the designated key.
  * System Parameter requirement: Programmatic management by non-admin users requires setting `base.enable_programmatic_api_keys = True` in Technical Settings.
  * Throttling cap: Default maximum of 10 programmatic API keys per user, configured via `base.programmatic_api_keys_limit`. Exceeding limits returns HTTP `422 Unprocessable Content`.
* **Recommended Service User Pattern:**
  * For the PMO adapter, create a dedicated bot user (e.g. `pmo_adapter_bot`) in Odoo.
  * Set an empty password on the user account (disabling interactive web login while allowing API key auth).
  * Assign the minimal model access rights required (Procurement, Invoicing, Project, Fleet, Maintenance).
  * Avoids personal credential leakage and keeps audit log fields (`create_uid`, `write_uid`) clean.
* *Primary Source:* [Programmatic Key Management](https://www.odoo.com/documentation/master/developer/reference/external_api.html#programmatic-key-management).

### 2.3 Hosting Options, Plan Restrictions, and Rate Limits

The operational constraints on the external API vary significantly depending on whether the prospect runs Odoo Community, Odoo Online (SaaS), or Odoo.sh.

#### 1. Odoo Community (Self-Hosted Baseline)
* **License:** LGPLv3 open-source.
* **API Access:** Full, unrestricted access to JSON-2 and legacy RPC. No licensing verification, paywall checks, or synthetic API caps exist in the Community codebase.
* **Limits:** Governed exclusively by the hosting server (CPU, RAM, Gunicorn workers configured in `odoo.conf`, and reverse-proxy rate limiting in Nginx/HAProxy).
* *Conclusion:* Community is the safest and most reliable hosting posture for high-throughput operational syncing without vendor billing interference.

#### 2. Odoo Online (Vendor SaaS)
* **Plan Restriction:**
  > *"Access to data via the external API is only available on Custom Odoo pricing plans. Access to the external API is not available on One App Free or Standard plans."*
  * Standard plan subscribers who attempt to connect via API are contractually blocked or risk automated account suspension.
* **Rate Limits (Cloud Acceptable Use Policy):**
  * Under section *Unthrottled RPC/API calls*:
    > *"Throttled calls are typically acceptable for unsustained usage at a rate of 1 call/second, with no parallel calls. On Odoo.sh the dedicated hosting mode can be considered as an alternative to lift this restriction."*
  * Sustained traffic exceeding **1 request per second** or sending concurrent/parallel requests triggers HTTP `429 Too Many Requests` and temporary IP ban.
  * Account storage limit: Accounts exceeding 100 GB are subject to mandatory audit or migration to Odoo.sh.
* **Adapter Implication:** On Odoo Online, a naive fine-grained sync will instantly fail against the 1 req/sec limit. The PMO adapter must batch calls into bulk arrays (`Model.create([vals1, vals2, ...])`) and throttle outbound requests.
* *Primary Sources:* [Odoo Acceptable Use Policy](https://www.odoo.com/acceptable-use), [Odoo Plans & Pricing](https://www.odoo.com/pricing).

#### 3. Odoo.sh (Cloud Platform) & On-Premise Enterprise
* **Plan Requirement:** Requires an active Enterprise Custom Plan license.
* **Limits:** Runs in dedicated Docker containers on Odoo.sh or on dedicated bare metal / virtual machines for on-premise. The shared SaaS 1 call/second rate limit does not apply; worker concurrency is sized by dedicated worker purchase.
* *Primary Source:* [Odoo.sh Platform Documentation](https://www.odoo.com/documentation/master/administration/odoo_sh.html).

### 2.4 Change Feed Architecture: Webhooks vs. Watermark Polling

Per ADR-0055 and ADR-0059, PMO implements a two-tier change feed: **webhooks for latency + watermark sweep for truth**.

#### Tier 1: Outgoing Webhooks via `base_automation`
* **Module Availability:** The `base_automation` module (*Automation Rules*) and the server action webhook engine (`ir.actions.server`) are part of the core open-source repository ([`odoo/odoo addons/base_automation`](https://github.com/odoo/odoo/tree/master/addons/base_automation), [`addons/base/models/ir_actions.py`](https://github.com/odoo/odoo/blob/master/odoo/addons/base/models/ir_actions.py)).
* **Community vs. Enterprise Configuration:**
  * **In Odoo Community:** Automation rules are fully functional out of the box with zero custom modules. They are configured via Developer Mode under *Settings ‣ Technical ‣ Automation ‣ Automation Rules*.
  * **In Odoo Enterprise:** Accessible via Developer Mode or visually through **Odoo Studio** (*Studio ‣ Automations*).
* **Outgoing Webhook Mechanism:**
  * Trigger types: *On Save*, *On Creation*, *On Update of specific fields*, *On Deletion*, or *On Time Condition*.
  * Action type: `webhook` (`Send Webhook Notification`).
  * Configuration: Set target URL (e.g. `https://<supabase-project>.functions.supabase.co/odoo-change-feed`), select target fields to include in the payload, and set optional headers.
  * Odoo dispatches an HTTP `POST` containing `{"_id": record.id, "_model": "purchase.order", ...fields}`.
* *Primary Sources:* [odoo/odoo PR #138804 (Native Webhooks)](https://github.com/odoo/odoo/pull/138804), [Odoo Automation Rules Documentation](https://www.odoo.com/documentation/master/applications/studio/automated_actions.html).

#### Tier 2: Watermark Reconciliation Sweep
* **Audit Fields:** Every standard model in Odoo ORM inherits automatic log access fields: `id`, `create_date`, `write_date`, `create_uid`, and `write_uid`.
* **Cursor Mechanism:**
  * The PMO adapter queries modified records using `search_read`:
    ```json
    {
      "domain": [["write_date", ">", "2026-10-30 07:00:00"]],
      "fields": ["id", "write_date", "name", "state"],
      "order": "write_date asc, id asc",
      "limit": 100
    }
    ```
  * Cursors store `last_synced_write_date`. Because `write_date` is stored in UTC PostgreSQL `timestamp without time zone`, timezone drift is avoided.
  * In both Community and Enterprise, this sweep acts as the reconciliation safety net to recover any events dropped during network partitions or webhook delivery timeouts.

### 2.5 Project Analytic Accounting Architecture (Costs & Revenues)

A critical requirement for the EPC prospect is linking site costs and revenues to specific construction projects.

#### 1. Core Model Hierarchy (`analytic.mixin`)
* In Odoo 16+, Odoo replaced the legacy single foreign key `analytic_account_id` on money lines with a flexible multi-plan distribution model based on `analytic.mixin` ([`addons/analytic/models/analytic_mixin.py`](https://github.com/odoo/odoo/tree/master/addons/analytic)).
* **Analytic Plans (`account.analytic.plan`):** Used to segment dimensions (e.g. *Projects*, *Departments*, *Cost Centers*).
* **Analytic Accounts (`account.analytic.account`):** Individual cost objects tied to a plan.
* **Analytic Distribution Field (`analytic_distribution`):**
  * Stored on line items as a `fields.Json` dictionary mapping analytic account IDs to percentage shares:
    ```json
    {"14": 100.0}
    // Split across two projects or cost centers:
    {"14": 60.0, "22": 40.0}
    ```
  * Present natively on:
    * Vendor Bill Lines: `account.move.line.analytic_distribution`
    * Purchase Order Lines: `purchase.order.line.analytic_distribution`
    * Sales Order Lines: `sale.order.line.analytic_distribution`
    * Expense Reports: `hr.expense.analytic_distribution`

#### 2. Project Mapping (`project.project`)
* Each `project.project` record carries a direct foreign key `analytic_account_id` pointing to `account.analytic.account`.
* When a project is created, Odoo can automatically provision a corresponding analytic account under the *Projects* plan.
* **Timesheets (`account.analytic.line`):**
  * In both Community and Enterprise, logging timesheets via `hr_timesheet` creates an `account.analytic.line` with `account_id = project.analytic_account_id.id` and `unit_amount = hours`.
  * Multiplied by the employee cost rate (`timesheet_cost` on `hr.employee`), this posts direct labor cost to the project's analytic ledger.

#### 3. Revenue & Procurement Cost Linkage
* **Procurement (PO ‣ Bill):**
  * When a site material request or PO is created in PMO and written down to Odoo, PMO populates `analytic_distribution: {str(project.analytic_account_id.id): 100.0}` on each `purchase.order.line`.
  * When Odoo validates the vendor bill (`account.move`), the analytic distribution copies to `account.move.line`, automatically posting financial debit lines to `account.analytic.line`.
* **Revenue (Sales Order ‣ Customer Invoice):**
  * Invoicing milestones or timesheets sets `analytic_distribution` on the invoice line, posting credit entries to the project's analytic ledger.

#### 4. Community Baseline vs. Enterprise Differences
* **What Community Has:**
  * Complete data structure: `account.analytic.account`, `account.analytic.plan`, `analytic_distribution`, `account.analytic.line`.
  * Vendor bill and PO analytic distribution tagging.
  * Timesheet cost generation (`hr_timesheet`).
* **What Enterprise Adds:**
  * **Project Profitability Dashboard:** A dynamic top-level summary widget embedded inside `project.project` displaying live cards for *Invoiced Revenue*, *To Bill*, *Timesheet Costs*, *Vendor Bills*, and *Margins*.
  * **Analytic Budgets (`account_budget`):** Setting theoretical budget amounts on analytic accounts with automated variance tracking (Enterprise-only module).
  * **Dynamic Financial Reports (`account_reports`):** Dynamic P&L filtered by analytic accounts.
* *Architectural Conclusion:* Because PMO natively owns budget versions, BoQ progress assessments, and project P&L calculations (per ADR-0055 \S 5 and ticket #1481), **PMO does not need Odoo's Enterprise profitability dashboard or budget module**. Odoo Community's stock analytic lines provide all the transactional ledger grounding PMO requires.
* *Primary Sources:* [Odoo Analytic Accounting Documentation](https://www.odoo.com/documentation/master/applications/finance/accounting/reporting/analytic_accounting.html), [Track Costs with Timesheets](https://www.odoo.com/documentation/master/applications/services/project/record_and_invoice/time_tracking.html).

## 3. Open Unknowns & Verification Flags

1. **JSON-2 Support in Pre-v19 Self-Hosted Deployments:**
   * *Status:* The JSON-2 API is the master reference standard documented for Odoo 19/20. If the prospect runs an earlier version (e.g. Odoo 17 or 18 Community), JSON-2 may not be present, requiring the adapter to fall back to standard JSON-RPC (`/jsonrpc` with `call` payload).
   * *Mitigation:* The PMO adapter client abstraction should support both JSON-2 and `/jsonrpc` calls transparently.
2. **Odoo Online Hard Enforcement of API Licensing:**
   * *Status:* Official documentation explicitly states API access is exclusive to the Custom Plan. While API keys can technically be created in UI on some trial databases, relying on API integrations on an Online Standard plan is a terms-of-service violation and risks automated suspension without notice.
   * *Recommendation:* The prospect must deploy on **Odoo Community self-hosted** or subscribe to the **Odoo Enterprise Custom plan** (preferably Odoo.sh or on-premise to avoid the 1 req/sec rate limit).
3. **Outgoing Webhook Failure Retry Policy:**
   * *Status:* In `base_automation`, if an outgoing webhook HTTP POST fails (e.g. target endpoint 500 or timeout), standard Odoo does not provide an exponential-backoff dead-letter retry queue for webhook deliveries.
   * *Mitigation:* Confirms ADR-0055's rule: webhooks provide low-latency notifications, but the **watermark reconciliation sweep** (`write_date` cursor) is mandatory for data consistency.
